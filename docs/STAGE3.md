# Stage 3 — إدارة المخزون

## الأساس والتوافق

الفرع `stage-3-inventory` يبدأ من `stage-2-sim-scanner` عند `7f312ef5cc5c349148f0030d6e200a5cc2d637c8`. طلب المرحلة الثانية #2 كان مفتوحًا ويستهدف `stage-1-foundation` وقت بدء العمل؛ لذلك يستهدف طلب هذه المرحلة فرع المرحلة الثانية. لا دمج تلقائي لأي مرحلة سابقة. بعد دمج الاعتمادات يمكن إعادة استهداف main.

لا تغيير في Room schema v1 أو `rb.db` أو `com.rb.app` أو UUID أو الأرقام الحالية. الإصدار `0.3.0`، versionCode=3. لا destructive migration، ولا سجل حركات أو سلة محذوفات أو تصدير أو مزامنة.

## الاستخدام

- تفاصيل المجموعة: اسم المسؤول ورقم المجموعة والعدد الفعلي، وصفوف صغيرة بآخر أربع خانات والرقم الكامل. الفرز رقمي تصاعدي أو تنازلي، مع الحفاظ على الأصفار والأرقام الطويلة.
- مربع التحديد أو الضغط المطوّل يبدأ التحديد؛ الضغط على صف في وضع التحديد يبدّل اختياره. زر المعلومات يفتح التفاصيل حتى أثناء التحديد. تحديد الكل يشمل القائمة المعروضة فقط.
- «تحديد نطاق»: اختر صف البداية ثم النهاية، ثم راجع العدد واضغط تحديد. الضغط المطول على صف قبل فتح النطاق يجعله البداية. يمكن أيضًا إدخال حدين من أربع خانات؛ يشمل ذلك جميع السجلات المطابقة الموجودة فقط، بما فيها النهايات المتشابهة. النطاق يستبدل الاختيار الحالي ولا يولّد أرقامًا.
- شريط الإجراءات السفلي ينقل المحدد أو يؤرشفه أو يحذفه بعد التأكيد. اختيار الوجهة يعرض رقم المجموعة ومسؤولها، ثم تأكيدًا بالعدد والوجهة. الرجوع يلغي التحديد أولًا.
- الأرشيف العام يعرض السجلات نفسها عندما `groupId=null`، مع العدد والبحث والتحديد والنقل إلى مجموعة والحذف المؤكد.
- البحث يطابق أي جزء متصل من الرقم الكامل، ويعرض كل المطابقات مع المسؤول ورقم المجموعة أو الأرشيف. يعمل أثناء الكتابة مع مسح سريع للنص. الأرقام العربية والفارسية تُطبّع إلى ASCII دون تحويل عددي.
- تفاصيل الشريحة تعرض الرقم الكامل وآخر أربع خانات والموقع ونسخ الرقم والنقل والأرشفة والحذف. نسخ الرقم لا يغيّر قاعدة البيانات.

## سلامة البيانات والأداء

`changeInventory` يستقبل لقطة من السجلات المحددة الفعلية، ويعيد التحقق من هويتها وأرقامها ومواقعها ووجود وجهة النقل داخل معاملة Room واحدة. تغير أي سجل أو حذفه يبطل الدفعة كلها. التحديث يمس `groupId` فقط، والحذف DELETE نهائي. تُجزّأ عبارات IN إلى 900 معرّف تحت المعاملة نفسها لتجاوز حد SQLite للمعاملات، دون تقسيم ذرية العملية. فشل كتابة متأخرة يتراجع عن جميع الكتابات السابقة.

الأعداد مشتقة من استعلامات Room ويُعاد بثها بعد التغيير. البحث يستعمل استعلام LEFT JOIN واحدًا لإظهار المواقع، ومطابقة `instr` حرفية دون wildcards أو استعلام لكل صف. تؤخر الكتابة الاستعلام 250ms وتلغي تدفق البحث السابق. بحث الجزء الداخلي يحتاج مسح النصوص؛ لا ادعاء باستعمال فهرس للبحث الجزئي. القائمة تُحمّل كسجلات وتُعرض عبر LazyColumn؛ لا تحميل صور أو رسم آلاف الصفوف دفعة واحدة. التقسيم إلى صفحات لقواعد ضخمة خارج حجم آلاف السجلات لم يُضف.

الفرز يقارن طول الجزء بعد إزالة الأصفار البادئة ثم نصه، مع الرقم الكامل والمعرف لكسر التعادل؛ لا CAST إلى Long/Double. الاختيار Set من UUID داخل ViewModel خاص بوجهة التنقل، فيبقى عند التمرير وإعادة التركيب وتدوير Activity. تغيير نص البحث يلغي الاختيار؛ السجلات غير المعروضة لا تدخل الإجراءات. لا تُستعاد موافقات أو حوارات تنفيذ بعد موت العملية؛ تبقى بيانات Room المحفوظة.

## التحقق

نجح محليًا بتاريخ 2026-11-13 الأمر `./gradlew testDebugUnitTest lintDebug assembleDebug` على JDK 17 وSDK 36: **61 اختبارًا ناجحًا، صفر فشل أو تجاهل**. Lint: صفر أخطاء و3 تنبيهات تحديث موجودة سابقًا لمكتبات Lifecycle/Navigation المثبتة لأسباب التوافق الموثقة في README. لا تغيير في schema الإصدار 1 بعد توليد Room. أُنتج Debug APK بحجم نحو 85 MiB؛ اجتاز `apksigner verify` بتوقيع v2، وظهر versionCode=3 وminSdk=26 وtargetSdk=36 دون صلاحية INTERNET. راجعت لقطة تفاصيل المجموعة الناتجة عن اختبار Compose. قواعد Compose للاختبارات تتبع API المشروع الحالي، مع تنبيه إهمال من المكتبة إلى v2؛ ليست أخطاء بناء أو اختبارات. اختبارات المرحلة الثالثة تشمل Room على API 26 و35، والنقل الفردي والجماعي والأعداد والهوية، والأرشفة والتوزيع، والبحث المتشابه والأصفار والفرز الطويل، والنطاقات، والوجهات المحذوفة واللقطات القديمة، ودفعات تتجاوز حد SQLite، وفشل تحديث وحذف باستخدام triggers. اختبارات Compose تتحقق من إلغاء الحذف والتأكيد، والضغط المطول والنطاق والأرشفة والتوزيع، والبحث والنسخ، وثبات التحديد عند التمرير والفرز وإعادة إنشاء Activity. تظل اختبارات المرحلتين السابقتين ضمن المجموعة.

## APK والتحديث

GitHub Actions يبني الاختبارات وLint وDebug APK ويرفع `Rb-stage3-debug` وتقارير التحقق. أضيف فرع المرحلة الثانية إلى قواعد تشغيل PR، مع الإبقاء على الفروع السابقة والتشغيل اليدوي.

رفع versionCode والحفاظ على قاعدة البيانات يسمحان بالتحديث **بشرط تطابق شهادة التوقيع**. مفتاح APK السابق غير متوفر في المستودع؛ توقيع Debug المؤقت في Actions قد يختلف. استخدم مفتاح النسخة المثبتة عند بناء تحديث لبيانات قائمة، وقارن `apksigner verify --print-certs` بين النسختين. لا تحذف التطبيق أو تمسح بياناته لمعالجة اختلاف التوقيع؛ لا يوجد استيراد/نسخ احتياطي في هذه المرحلة. لم تتغير آلية توقيع المشروع أو تُضف مفاتيح إلى Git.

لا يوجد هاتف فعلي متصل؛ اختبارات Robolectric لا تقيس دقة الكاميرا أو OCR على عتاد الهاتف. قيود المسح واختبار البطاقات الفعلية موثقة في STAGE2.md.
